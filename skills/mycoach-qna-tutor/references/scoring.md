# 对练记录评分

用于本技能内的对练，也用于用户提交的两个人之间的文字、录音、视频或已有转写。先读[16项原量尺](exam-standard.md)及[机器可读量尺](exam-standard.json)。评分是有证据的练习评价，不写网站成绩、毕业结果或考试系统。

## 先识别可评价的证据

识别谁是Coach、谁是顾客、题目和用户希望评谁。根据称呼与对话内容可以判断时直接说明采用的角色映射；角色确实不清则先问清，只继续独立的记录整理。多人记录按人分开评价。用户自述“我操作成功”属于自述，顾客反馈、视频所见和考官记录分别标注。

内部核对时保留对话顺序和原有时间码；内部编号不展示给学员。给评价时直接引用原话，有时间码则用实际时间定位。原文只作必要的短引用，疑似转写错误且影响技术判断时标“转写待核”，不擅自改成有利或不利证据。无法打开的文件、没有实际读取的音视频不进入评分依据。真实密码、验证码与联系方式不复述。

先判断是完整一轮、明确片段，还是完整性不明。片段没出现开场/收尾，不等于Coach没做；完整记录明确缺失必需动作，才能按相应档位或“无”评价。评分不依赖人设外的未披露信息，也不能从顾客一句“好”推出操作成功。

## 内部计分状态

下列英文键只供计分脚本使用，不显示在学员评价中。对外写“做到了”“这次没做”“仅凭文字暂不能判断”“这段没有记录”。

## 每项的四种状态

| 状态 | 如何处理 |
| --- | --- |
| `observed` 有足够证据 | 依原始档位评0–10或有/无，给具体原话与理由。技术错误必须核对官方适用条件。 |
| `not_done` 完整记录证明未做 | 数值项依原档位评；流程项按原“无”标准判断，不能仅凭未出现关键词判无。 |
| `unobservable` 媒介无法观察 | 如仅文字无法判断语气、眼神、实机演示清晰度，分数留空，说明缺少什么。 |
| `missing` 记录范围未覆盖/转写待核 | 分数留空；说明需补哪个片段或信息，不当成0分。 |

一项可能同时含文字能评与媒体不能评的要求。不能观察的部分会实质影响该项档位时，整项暂不定分，列出已观察优缺点。完整文字转写能评价表达、逻辑和互动证据，但不能据此宣称“自信大方”“语气热情”“全程演示清晰”。不要强行给16项满表确定分数。

当用户提供的是行为摘要而非逐字稿，摘要没给出具体原话或类比属于证据缺口；不能据此认定讲解生硬、缺乏类比并扣分。只评价摘要明确记载的动作，其余保留未知。

## 计分口径

数值项原始0–10；流程项“有”=10、“无”=0。每项折合贡献 = 原始分/10 × 维度权重 × 该项维度内权重/100。四维度分别为30、35、25、10，总分100。**不要把16项直接平均，也不要把四维度简单平均**。

证据完整、16项都能定分时，可给“本次模拟总分 X/100”，并说明按现有MyCoach模拟口径≥80为通过。该线是项目模拟规则，正式考试判定须以当期通知为准。历史原分数和评语保留原口径，不能和本次模拟分混算。

有未观察/缺失项时，内部计算三个量。默认对外只给明确标为“可评部分参考分”的归一化结果，并用一句话说明哪些不能评；不展示S/W、算术区间或多套数字。用户明确要求核对计算时，再说明以下细节：

1. **已观察项折合得分 S / W**：W是这些项目在原100分中的总权重，S为实际折合分。
2. **表现参考值 S/W×100**：仅对已观察项归一化，明显标为局部参考，不能用它宣布整场通过。
3. **整场可确定区间 [S, S+(100−W)]/100**：未观察项目取0到满分的边界，不当作已得分。区间跨过80时说明无法判定整场是否达到模拟线。

若无任何可评分项，给证据缺口及补充方向，不造分。区间是算术边界，不是概率或预测。使用 `python3 scripts/score_record.py --input <file.json>` 可以确定性计算；脚本不会理解对话，分数与证据必须先由AI按原档位判断。没有Python时按同一公式手算并复核。

输入形状：

```json
{
  "record_scope": "partial",
  "medium": "text",
  "items": {
    "qna-01": {"status": "missing", "score": null, "evidence": [], "reason": "只收到排障片段，没有开场"},
    "qna-12": {"status": "observed", "score": 3, "evidence": ["T008 Coach：上限80%就是电池健康只有80%。"], "reason": "将充电上限等同最大容量属于严重概念错误，依第12项原0–4档评价；3分仅为格式示例"}
  }
}
```

这只是格式示例，不能把所有技术错误固定评成3分。先按原档位区分严重概念错误、部分不准确和表达不完整，再根据实际证据定分。其余未提供项由脚本保留为missing；不给默认满分。`not_done`必须注明完整记录与缺失动作，数值不自动固定0分，要按档位解释。

脚本按现有项目的运算次序累计各维度未舍入值，再计算总分并保留两位小数；不要先逐项四舍五入后相加。逐项展示值相加与未舍入总分偶尔可能差0.01，保留总分的原计算口径。

## 同时检查服务流程

按[六环节流程](service-flow.md)另给一份简短查漏：欢迎与称呼，认同/共鸣/尽力保证，探需意图及型号/系统/时间/触发/已试方法，复述确认，每项操作目的/同意/验证及其他问题，企微反馈/支持App用途/评价/产品兴趣/道别；适用时加售后诊断。每条引用记录位置，区分已做到、完整记录证明未做、片段未覆盖和无法观察。

查漏用于改进，不构造第17项或改变权重。某个流程动作没有出现，应结合该项原档位解释实际影响；不能仅因没问称呼或其他产品兴趣，就把原第1项或第16项直接判无，或另设流程加减分。原文的寒暄“加分项”也不能额外加分。原始量尺没有的动作可提建议，不能冒充原量尺硬条件。质量分支的时间、备用机与数据保证按当次已核实的服务安排核对。

## 反馈交付

先用两三句说本次整体表现；有完整证据时给单一模拟总分。证据不全时，写“能评的部分，表现参考约XX分；语气/实机演示等还不能评，这不是完整考试总分”。分数必须来自内部原量尺计算，不能为了显得简洁而编一个总分。

接着给最值得改的两三处，每处直接引用原话，再写下次怎么说或怎么做。确有证据的优点也说明。默认不铺16行大表；用户要“逐项评分”时再按原16项列三列：“检查内容｜这次表现或得分｜原因和改法”。数值项一套分数，流程项写“做到了/这次没做”，未知项写中文原因；不显示英文状态、内部代号和折合分。

例如：“您说‘那就好了，谢谢，再见’后就结束了，少了其他问题和后续联系。下次可以接一句：‘您还有别的问题想问吗？回去要是还有问题，您在企业微信上给我留言。’”

技术纠错附相关Apple官方链接；来源编号与计算日志保留在内部核对资料，学员不用对照代号找原话。最后给一个针对性的重练建议即可。

不因为记录很长、使用术语、顾客道谢或历史案例通过就直接高分。仍按原档位判断，不用关键词次数、情绪标签或职业刻板印象给分。详细算式、分数区间与机器字段只在用户明确要求时展示。
